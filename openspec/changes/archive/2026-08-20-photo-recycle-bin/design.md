## Context

空仓库起步，需求只有三条：申请相册权限、缩略图网格、大图页手势 + 恢复按钮。技术栈无历史包袱，按 iOS 原生最简方案落地。

约束：立项时开发机只装了 Command Line Tools，没有 Xcode，编译不了 iOS target。因此工程结构要保证「纯逻辑部分在没有 Xcode 时也能跑测试」。2026-08-20 已补装 Xcode 16.1（iOS 18.1 SDK）与 iOS 18.1 模拟器 runtime，编译、`swift test`、模拟器运行都已跑通。

2026-08-20 用户澄清：删除必须最终落到系统相册的「最近删除」，原先的「纯应用内软删除」不满足需求。本文件的决策 1 已按两段式重写。

## Goals / Non-Goals

**Goals:**
- 一个能在 Xcode 里直接打开、编译、跑起来的最小可用 App。
- 上滑删除有明确的防误触阈值和实时视觉反馈。
- 提交前误删可恢复，且恢复入口在任何页面都可达。
- 暂存区逻辑可被单元测试覆盖。

**Non-Goals:**
- 不做「从系统『最近删除』恢复」——PhotoKit 未开放该能力（见决策 1）。
- 不做上滑即删（单张立刻调用 PhotoKit）——每张都会弹系统确认框，与连续清理冲突。
- 不做视频、Live Photo、iCloud 未下载资源的特殊处理，只取 `.image`。
- 不做相册分组、搜索、多选、分享、编辑。
- 不做 iPad 适配与横屏布局。

## Decisions

### 1. 删除分两段：应用内暂存 + 一次性提交到系统「最近删除」

需求要的最终落点是系统相册的「最近删除」，同时需求 3 又要求「可恢复误删图片」。这两条无法同时由应用满足：

- `PHAssetChangeRequest.deleteAssets` 确实会把资源移入「最近删除」（`PHAssetChangeRequest.h:40`）；
- 但 iOS 18.1 SDK 的 `Photos.framework` 里**没有任何**恢复通道——`PHAssetCollectionSubtype` 从 200 到 219 共 20 个子类型不含「最近删除」，整个 Headers 目录 grep `recentlydeleted|trash` 零命中。第三方 App 既列不出也恢复不了其中的资源。
- 而且这些照片不是本应用创建的，每调一次 `deleteAssets`，系统都会弹一次确认框。上滑一张弹一次，连续清理无法进行。

所以拆成两段：

1. **暂存**——上滑只把 `localIdentifier` 记进本地暂存区，网格与大图页过滤掉这些 id，系统相册原图不动。此阶段「恢复」按后进先出即时撤销，成本为零。
2. **提交**——底部「删除 N 张」把暂存区里的资源一次性交给 `deleteAssets`，系统只弹一次确认框，全部进入「最近删除」。提交成功后清空暂存区；用户取消（`PHPhotosError.userCancelled`，3072）则暂存区原样保留。

代价：提交前不释放存储空间；提交后应用侧不再有恢复入口，用户需自行去系统「照片 → 最近删除」找回（30 天内有效）。这是 PhotoKit 的硬边界，不是实现取舍。

### 2. 翻页方向跟随系统相册（左滑 = 下一张）

需求原文写的是「左滑上一张，右滑下一张」，与 iOS 系统相册相反。2026-08-20 与用户确认后改为跟随系统习惯：手指向左滑看下一张，下一张从右侧跟手滑入。

实现上把页面按 `x = (i - currentIndex) * width` 排布，手指位移直接叠加为 offset，视觉与手指方向一致，不会出现「滑进来的是 A、松手却跳到 B」。

### 3. 自研分页，不用 `TabView(.page)`

`TabView` 会吞掉同一区域的竖向 `DragGesture`，没法和上滑删除共存——这是决定性原因。

自研分页只渲染 `index-1 / index / index+1` 三页，避免几千张照片全部进视图层级。

### 4. 手势轴锁定 + 上滑阈值 = 屏幕高度的一半

一次拖拽只走一个轴：首次位移超过 10pt 时按 `|dx|` 与 `|dy|` 谁大锁定轴，锁定后不再切换，避免斜着滑时又翻页又删除。

竖向只响应向上（`dy < 0`）。松手时 `-dy > 屏幕高度 / 2` 才移入回收站，对应需求里的「超过一半，避免误操作」。拖拽过程中图片跟手上移并逐渐变淡，越过阈值时提示文案从「上滑移入回收站」变为「松手移入回收站」，让阈值可感知。

### 5. 「恢复」按钮在网格页也出现

需求原文把「恢复」按钮挂在大图页。但如果把最后一张照片移入回收站，大图页会自动关闭，恢复入口随之消失，「可恢复误删图片」就不成立了。因此网格页在回收站非空时展示同一个底部条。属于补齐既定状态的遗漏，不是新增功能。

「恢复」的语义是撤销最近一次移入（后进先出）。在大图页恢复后，视图会跳到被恢复的那张，让操作结果可见。

### 6. 纯逻辑抽成 SwiftPM target

`RecycleBin`（入站顺序、恢复、去重、失效 id 清理）只依赖 Foundation，放在 `SPhoto/Core/`，同时被：
- 根目录 `Package.swift` 的 `SPhotoCore` target 编译 —— 用于 `swift test`，在没有 Xcode 的机器上也能跑；
- Xcode app target 直接编译 —— app 不通过包依赖引入，避免为一个文件在工程里挂本地 package。

代价是这批文件被两处编译，需要保持零 UIKit/SwiftUI/Photos 依赖。

### 7. 部署目标 iOS 17，SwiftUI + `@Observable`

`@Observable` 比 `ObservableObject` 少一半样板代码，要求 iOS 17。iOS 17 已发布近三年，对个人项目不构成覆盖问题。

### 8. Info.plist 用构建设置生成

用 `GENERATE_INFOPLIST_FILE = YES` 加 `INFOPLIST_KEY_NSPhotoLibraryUsageDescription`，不单独维护 Info.plist 文件，少一个文件和一组工程引用。

## Risks / Trade-offs

- **提交删除只能真机/模拟器手验**：`deleteAssets` 的系统确认框走 SpringBoard，无法用命令行代点，自动化测试覆盖不到「点确认 / 点取消」两条分支，只能人工走一遍。
- **暂存不释放空间**：只有点了「删除 N 张」提交之后，照片才进系统「最近删除」，空间也要等系统清空「最近删除」（30 天或用户手动）才真正释放。
- **提交后应用侧不可恢复**：见决策 1，属 PhotoKit 硬限制。UI 上「删除 N 张」依赖系统确认框做最后一道拦截，应用内不再叠加二次确认。
- **`PHFetchResult` 与外部变更**：应用注册 `PHPhotoLibraryChangeObserver`，相册在后台被改动时重新拉取，避免索引越界。仅授权「选中部分照片」时，能看到的就只有用户选中的那部分。
